1At a glance

    2Results contract

    The run_id hashes the config, not the code, and sweep skips every (run_id, seed) already in the results file. A change that alters any number a run produces must therefore be opt-in, or the old rows silently become incomparable with new ones. Each proposal carries one of four labels that say how it may land.

    A Identical

    Same outputs bit for bit, verified by benchmark. Lands in place; add a regression test comparing outputs before and after.

    B Float-level

    Same math, but a different reduction or batching order can move the last bits. Lands in place with an allclose test; say so in the commit message.

    C Opt-in

    Changes numerics or an RNG stream. Needs a new kwarg whose default keeps the old behaviour, or a new registered variant. Changes the run id only when set.

    D Bookkeeping

    Touches only caches, I/O or the sweep driver. No run output changes; cache-key tests in tests/test_cache_keys.py must stay green.

    3Where the time goes

    A frozen-backbone CUB run of the Koh et al. anchors (the configuration every cub_koh2020* ablation repeats), on the cached Inception features, split by pipeline step with wall-clock timers around each step. The concept phase runs to the 200-epoch cap in both anchors; the independent head phase does too, while the sequential head stops early.

    Mapped onto the pipeline, the proposals below concentrate on the training stage, the evaluators and the per-run setup that a sweep repeats for every config.

    Highlighted stages have at least one proposal. IDs link to it.

    4Measured speed-ups

    Each bar compares the current code path with the proposed one on CUB-sized inputs (4,796 train / 1,198 val / 5,794 test images, D = 2048, K = 112 concepts, C = 200 classes), calling the library's own functions. The two end-to-end bars (reused context, cached val) come from the Modal runs above. Every comparison also checked that the outputs match. Hover a bar for the before and after times.

    5Fine-tuning on the GPU

    The fine-tuned anchors (finetune: on Inception-v3, up to 300 epochs at roughly 15 s each) are the most expensive runs in the study. Two measurements on an A100 show how much faster a step could be, and how much of that a real epoch would see.

    A real epoch also loads and augments the images. The second chart runs one warm epoch of the cub_koh2020 loop on the anchor's own _ImageFeed loaders (8 workers, 16 vCPU) and splits it into time spent waiting for the next batch and time spent computing.

    8Rollout

      9Method

      CPU. Apple M-series laptop, 10 cores, 8 torch threads, torch 2.14.1. Micro-benchmarks call optimize, ScoreLayer, SparseHead, SelectFilter, CUB, ResultsStore and InceptionBackbone directly, on random tensors of CUB shape (Inception with random weights where only timing matters). Each comparison also checks that the outputs match.

      GPU. scripts/speedup_bench_modal.py on this branch, torch 2.8.0, the same image as koh2020_modal.py. main runs the micro-benchmarks on an A100 (the container reported an A100 80GB PCIe). profile runs both frozen Koh et al. anchors on an L4 container with 8 vCPU, reading the cached Inception features on the cbm-koh2020 volume, and times each step with wall-clock wrappers (cProfile dropped outer frames on Python 3.12 and inflated the small training calls). epoch runs two epochs of the cub_koh2020 fine-tuning loop on the anchor's _ImageFeed loaders, 16 vCPU, and reports the second.

      uv run modal run scripts/speedup_bench_modal.py            # A100 micro-benchmarks
uv run modal run scripts/speedup_bench_modal.py::profile   # frozen CUB runs, time per step (L4)
uv run modal run scripts/speedup_bench_modal.py::epoch     # fine-tuning epoch: data wait vs compute (A100)

      Speed-ups on other hardware will differ. The ratios for removed work (recomputation, double forwards) are the most portable. The fine-tuning ratios depend on the GPU generation.
